# Robot Middleware & Orchestration Architectures: A Design Reference for a "One Brain, Many Bodies" Robot Brain

> Provenance: generated 2026-07-29 via Claude's deep research feature, commissioned during brain planning. This document is preserved verbatim as the citation base for the ADR log (docs/adr/). It is a point-in-time survey; the "mid-2026" claims should be re-verified before major dependency decisions.

## TL;DR
- **Do not adopt ROS 2 wholesale as your brain core.** For a solo, software-first builder doing B2B inspection/sensing with no manipulation, ROS 2's DDS discovery overhead, macOS friction, and C++/colcon complexity are net negatives. Steal its *patterns* — typed pub/sub, QoS semantics (Deadline/Liveliness/Lifespan), actions with feedback, and MCAP logging — but build a thin WebSocket adapter protocol yourself, modeled on Viam's "generic API + drivers + capability discovery" and Home Assistant's "config-flow declares capabilities / entity class defines the interface" split.
- **The winning orchestration shape is a three-tier fast/slow loop**, exactly as Figure's Helix (S2 VLM at 7–9 Hz, S1 policy at 200 Hz, plus a whole-body control tier at 1 kHz in Helix 02) and the SayCan lineage established: an LLM slow loop for planning, a local reflex/behavior-tree fast loop for reactive control and safety, and (later) learned policies. Keep the LLM out of the safety-critical path; it proposes, a deterministic validator disposes.
- **Build the "scar-tissue" scaffolding before any motor exists**: full-fidelity MCAP-style event logging with correlation IDs and monotonic clocks; a command validator + tiered watchdog/heartbeat (ArduPilot uses ~1 s for the direct-control link, ~5 s for the supervisory link); command TTL/lifespan so stale commands auto-expire; and a versioned handshake (MCP-style: client sends version, server echoes-or-alternatives, disconnect on mismatch) so old bodies don't break as the brain evolves.

## Key Findings

1. **ROS 2's biggest weakness is exactly your deployment profile.** Its default DDS transport does not scale gracefully over Wi-Fi and heterogeneous networks. The MoonBots team (Blaha et al., arXiv:2511.01437, "Designing for Distributed Heterogeneous Modularity") reported that DDS was "not reliable enough to support more than four robots transmitting only basic joint and state information" — and this was despite "a high-end Wi-Fi 7 setup"; they "migrate[d] within a day" to Zenoh, which resolved the issues. DDS's peer-to-peer discovery floods the network, and payloads over 64 KB show "sharp latency spikes and transmission failures," with process crashes reported at ≥128 KB in one study. This is why Open Robotics and Intrinsic jointly investigated a non-DDS RMW, "determined that Zenoh is the best potential fit for the needs of ROS users," and OSRF shipped native Zenoh as an experimental RMW for ROS 2 Jazzy, Rolling, and Iron.

2. **Viam is the closest existing analog to your idea and worth studying closely.** It treats hardware like cloud infrastructure ("a container runtime for hardware"): every component/service exposes the *same* protobuf API regardless of hardware (`Motor.from_robot(...).get_position()` works whether it's a Pi GPIO motor, a CAN stepper, or an ODrive), drivers ("modules") run as separate gRPC child processes registered via a `Ready` RPC, and a generic `DoCommand` escape hatch exists on every resource for anything the standard API doesn't cover. This "opinionated APIs + generic fallback" pattern is exactly the shape you want.

3. **Home Assistant proves the adapter model scales to over a thousand integrations** (Home Assistant "ships with more than a thousand built-in integrations," with community guides citing 2,000+ integrations / 3,000+ devices as of 2026) by separating two concerns: a *device integration* handles connection/config (via a "config flow" that declares capabilities and supports versioned migration), while an *entity integration* defines the abstract capability class (light, sensor, switch) with a `device_class` carrying machine-readable semantics. New device types plug in without the core changing.

4. **Behavior trees have largely won over FSMs for reactive orchestration**, and the modern pattern is *LLM-generates-BT*: the LLM plans and emits a behavior tree, which then executes deterministically and reactively. BTs generalize FSMs, decision trees, and the subsumption architecture, and become easier to maintain than FSMs as task complexity grows.

5. **The fast/slow split is the consensus architecture for LLM-in-the-loop robotics.** SayCan grounds LLM proposals with skill affordance value functions; per Ahn et al. ("Do As I Can, Not As I Say," arXiv:2204.01691), PaLM-SayCan "achieves a planning success rate of 84% and execution success rate of 74% in the training environment and 81% planning and 60% execution in a real kitchen," roughly halving errors versus an ungrounded LLM. Helix runs a 7B VLM slow loop and an 80M reactive policy fast loop as *separate processes* so each iterates independently; both run onboard with no cloud dependency and sub-100 ms control latency. The LLM's job is semantics and sequencing, not real-time control.

## Details

### 1. Prior-art landscape and what to steal

**ROS 2 (Robot Operating System 2).** ROS 2 is the de-facto robotics middleware. Architecturally it is a layered stack: user nodes → ROS Client Library (RCL) → ROS Middleware interface (RMW) → DDS. Communication primitives are **topics** (pub/sub streaming), **services** (request/reply), and **actions** (long-running goals with feedback and cancellation). DDS gives it decentralized discovery (no ROS 1 master single-point-of-failure), and **QoS profiles** let you tune reliability (best-effort vs reliable), durability (transient-local to serve late joiners), history/depth, and — most relevant to you — **Deadline** (max time between messages), **Liveliness** (how a publisher asserts it's alive, with a `lease_duration`), and **Lifespan** (how long a message stays valid before auto-expiry).

*What it gets right (steal these):* typed IDL messages with code generation; the topics/services/actions trichotomy; QoS as an explicit contract; the RMW abstraction (transport is swappable); and rosbag2/MCAP logging. The Deadline/Liveliness/Lifespan triad maps *directly* onto your heartbeat and command-TTL needs and is worth copying conceptually even though you won't use DDS.

*Known pain points:* DDS discovery overhead and poor Wi-Fi behavior (documented above); large-message fragmentation failures; steep debugging curve across a graph of many nodes; C++/`colcon`/workspace complexity; and the classic beginner mistake of "treating ROS like a local library" — writing nodes that assume instant, ordered, lossless delivery, then having everything break on real Wi-Fi.

*macOS/Apple Silicon:* Officially macOS is a lower-tier/"best-effort" platform and the UX lags Linux. In practice you *can* run it — RoboStack/`pixi` (conda-based) and Homebrew source builds work, native Apple Silicon builds are "ridiculously fast" (one practitioner reported an 18.5 s build vs 5–10 min on an old i7), and as of 2026 there's a demo of ROS 2 Kilted running natively on Apple Silicon with Gazebo, ros2_control, MoveIt 2, and Nav2 — but the reporter explicitly called it "a serious preview, not guaranteed production support—yet," and GUI tooling (rqt/RViz Qt bindings) remains the fragile part. **Verdict:** fine for optional simulation/experiments; not a reason to base your brain on ROS 2.

*When adopting ROS 2 wholesale is/isn't justified:* Justified if you need the existing ecosystem (Nav2, MoveIt 2, ros2_control, hardware drivers, SLAM) and run primarily on Linux/Jetson with wired or controlled networks. **Not justified** for your case — solo builder, software-first, LLM-centric brain, heterogeneous bodies incl. ESP32, macOS dev, inspection/sensing (no manipulation stack needed). You'd pay the full complexity tax for a fraction of the value. A ROS 2 *bridge adapter* (one body type that speaks ROS 2) is a better use than making ROS 2 your core.

**Viam.** A distributed system that treats physical hardware like cloud infra. `viam-server` runs on Linux/Mac/microcontroller, pulls config from the cloud (or local), and manages component/service lifecycles. **Components** map to physical things (camera, motor, sensor, board); **services** are algorithms (SLAM, vision, motion, navigation). Each type has an opinionated protobuf API with **generic fallbacks** (`generic` component/service, and `DoCommand` on *every* resource for arbitrary calls — per Viam's docs, "All resource APIs contain the generic DoCommand method to implement any functionality that does not fit into other API methods"). Drivers are **modules** — separate processes managed by `viam-server`, communicating over gRPC/UNIX sockets, that "register [their] models and APIs with viam-server through the Ready RPC"; `viam-server` then "calls ValidateConfig to check attributes and discover dependencies" per resource. Clients discover a machine's resources via `ResourceNames`/`GetMachineStatus` plus gRPC server reflection, and control uses gRPC over WebRTC (falling back to direct gRPC). A **Modular Registry** (npm/PyPI-for-robots) distributes drivers.

*What to steal:* the entire "standardized API per capability type + `DoCommand` generic escape hatch + swap hardware without changing app code" model; the driver-as-separate-process pattern; capability discovery via a resource-listing RPC + reflection; and config-driven instantiation. This is your adapter protocol's north star.

**Behavior Trees vs FSMs vs LLM planners.** BTs (BehaviorTree.CPP in C++, py_trees in Python) organize control flow hierarchically — Sequence, Fallback, Parallel, Decorator control nodes; Action/Condition leaves returning Running/Success/Failure. Colledanchise & Ögren showed BTs are a strict generalization of FSMs, decision trees, subsumption, and sequential behavior composition. Empirically (Iovino et al.), robot *behavior* is independent of representation, but **maintaining a BT becomes easier than an FSM as task complexity grows** — FSMs suffer a reactivity/modularity blowup as states and transitions multiply. Nav2 uses BTs as its core navigation orchestration for exactly this reason (runtime-loadable, reusable primitives, no recompilation). The modern combined stack: **LLM as BT-planner** — the LLM decomposes a natural-language goal into a BT, a validator/SMT-solver checks it, and a Failure Interpreter re-prompts the LLM when execution fails. *For you:* use an FSM for the brain's own top-level lifecycle (BOOT → IDLE → ACTIVE → DEGRADED → E-STOP), and BTs (or a BT-like structure the LLM emits) for task orchestration.

**LeRobot / VLA stacks.** Hugging Face's LeRobot is the open-source hub for imitation learning, RL, and vision-language-action policies in PyTorch (π0/π0-FAST from Physical Intelligence, SmolVLA, X-VLA, and world-model policies like VLA-JEPA in v0.6.0, released July 7, 2026). VLAs take multi-view images + proprioception + a language instruction and output continuous actions, typically via flow-matching/diffusion action heads on a VLM backbone. **Where they fit relative to your brain:** VLAs are the *skill/policy tier* (the "S1" reactive controller or a learned skill), NOT the orchestration brain. They're overwhelmingly about manipulation, need GPUs (CUDA) to train, and are irrelevant to your no-manipulation inspection use case for now. Keep LeRobot on your radar as a future "learned body driver," not as core infrastructure.

**Home Assistant (non-robotics analog).** All entities/services come from **integrations**, each owning a domain. The scaling insight is the two-layer split: (1) *device integrations* (e.g., Hue) handle the connection and are configured via a **config flow** (UI-driven, versioned — per HA docs, "we will be able to migrate configuration entries to new formats if the version changes"); (2) *entity integrations* (light, sensor, switch) define abstract capability classes with standardized state/attributes/services and a `device_class` for semantic typing ("Extra classification of what the device is... Device classes can come with extra requirements for unit of measurement and supported features"). An **Integration Quality Scale** (Bronze→Platinum, with rules like "must be fully async," "must clean up entity/device registry," "must have a code owner," "must implement diagnostics") drives ecosystem quality. *Steal:* the device-vs-capability separation, the config-flow onboarding with schema versioning/migration, semantic device classes, and a quality checklist for third-party body adapters.

**Other prior art.**
- **Zenoh** — a pub/sub/query protocol by former DDS developers, designed to fix DDS's discovery-flood and WAN problems. Benchmarks (Liang, Yuan & Lin, arXiv:2303.09419), single-machine latency: Zenoh P2P 10 µs, Zenoh brokered 21 µs, MQTT 73 µs, Kafka 27 µs, CycloneDDS 8 µs (via UDP multicast), and `zenoh-pico` 5 µs — note DDS actually *beat* Zenoh on the single-machine wired test, and Zenoh's advantage shows up on Wi-Fi/4G. Zenoh claims 1–2 orders of magnitude throughput over MQTT/Kafka and ~2× DDS throughput. Now an official ROS 2 RMW alternative.
- **MQTT** — lightweight broker-based pub/sub, the IoT default; NVIDIA's fleet dispatch uses MQTT + VDA5050. Its **Last Will & Testament** (broker auto-publishes a "will" message when a client dies, typically after ~1.5× the keep-alive interval) + retained status topics is the canonical "device dropped" pattern.
- **NVIDIA Isaac** — not a middleware competitor but a GPU-accelerated *layer on ROS 2* (Isaac ROS = CUDA-accelerated perception GEMs/NITROS pipelines on Jetson) plus simulation (Isaac Sim on Omniverse), robot learning (Isaac Lab), and humanoid foundation models (GR00T). Relevant only if/when you add heavy perception on Jetson bodies.
- **Agent frameworks applied to robotics / MCP** — MCP ("USB-C for AI", JSON-RPC 2.0 client-server) is increasingly used to give LLMs typed tool access; there's already a ROSBag MCP server (arXiv:2511.03497) for analyzing robot data via natural language. But researchers warn that naive MCP in robot control degenerates into a "rigid 'call tool–return result'" mode lacking lifecycle management, becoming "a stitching monster" without sandboxing, error feedback, and execution monitoring. **Use MCP for tools/introspection, not as your real-time control bus.**

### 2. Adapter/driver protocol design

**Capability declaration & discovery.** The proven pattern (Viam + Home Assistant): a body connects, then *declares* what it is and what it can do, in machine-readable form. Concretely:
- Give each body a **manifest/descriptor** at handshake: body ID, hardware class, firmware/protocol version, and a list of **capabilities** each typed by a standard capability class (`camera`, `microphone`, `speaker`, `differential_drive`, `range_sensor`, …) with attributes (resolution, rate, units). This mirrors HA's `device_class`-with-requirements and Viam's `ResourceNames`.
- Provide an **opinionated API per capability type + a generic `do_command` escape hatch** on every capability (Viam's exact model) so a body can expose non-standard functionality without you minting a new schema each time.
- Let the brain **query/discover** capabilities (a `list_capabilities` message ≈ Viam `ResourceNames`/`GetMachineStatus` + gRPC reflection). Keep discovery *pull-based and explicit* rather than DDS-style broadcast flooding.

**Message schemas & versioning.** This is where old bodies break if you're careless. Best practices, drawn from Protobuf, event-sourcing, and the MCP/WebSocket specs:
- **Adopt a version-negotiation handshake.** Copy MCP's lifecycle: the body sends its supported protocol version in an `initialize`/`hello` message; the brain "MUST respond with the same version (if supported), OR a different version it supports," and the client "disconnects if not" supported. Use **date-based or semver identifiers bumped only on backward-incompatible changes** (MCP: version strings "indicate the last date backwards incompatible changes were made... not incremented... as long as the changes maintain backwards compatibility"), and treat effective capabilities as the *intersection* of what both sides support.
- **At the transport layer**, RFC 6455 gives you `Sec-WebSocket-Protocol` for subprotocol negotiation ("The server selects one or none of the acceptable protocols and echoes that value"). The RFC's explicit guidance: prefer **reusing one subprotocol string and designing the payload schema for extensibility** ("Backward-compatible versioning can be implemented by reusing the same subprotocol string but carefully designing the actual subprotocol to support this kind of extensibility") over minting a new string per version (which WebSocket treats as a completely separate protocol).
- **Make the payload schema additive-only.** Follow Protobuf's field discipline even if you use JSON: "Once assigned, a field number should never be reused within the same message type. When you need to remove a field, mark it as reserved." Always add new fields with safe defaults, and never change a field's meaning. This gives you backward compatibility (new brain reads old body) and forward compatibility (old body ignores unknown fields).
- **Upgrade order matters:** in schema-registry practice, use BACKWARD compatibility as the default and **upgrade consumers before producers**; for unavoidable breaks, run **versioned parallel channels** (`telemetry.v1`/`telemetry.v2`) until all bodies migrate. For long-lived event logs, use **upcasting** (transform old event versions to new on read).

**Transport choice tradeoffs.** For a hobbyist-to-startup, heterogeneous fleet (laptop, ESP32, Pi, Jetson):

| Transport | Strengths | Weaknesses | Fit |
|---|---|---|---|
| **WebSocket (JSON/CBOR)** | Universal, trivial from TS/Python, firewall/NAT-friendly, browser-native, easy to log/inspect | Not the lowest latency; you build your own pub/sub, QoS, discovery | **Best default for your brain↔body control plane.** Matches your TS/React/Python skillset; ESP32 has WS libraries; laptop body is trivial |
| **MQTT** | Broker-based fan-out, LWT for death detection, tiny clients, IoT-standard | Broker is a dependency/SPOF; request/reply is awkward | Strong for **fleet telemetry / many-body fan-out** later; great LWT semantics |
| **Zenoh** | Best Wi-Fi/4G latency, P2P or brokered, `zenoh-pico` for MCUs, scales past DDS | Younger ecosystem, another dependency | Consider as a **high-rate data-plane** upgrade if WS latency bites |
| **gRPC** | Typed (protobuf), streaming, reflection/discovery, mature | HTTP/2 heavier on MCUs; less browser-friendly | Good if you want Viam-style typed APIs + reflection; heavier on ESP32 |
| **DDS** | Real-time, rich QoS, wired-LAN performance | Discovery flooding, poor Wi-Fi, heavy, complex | **Avoid** unless you commit to ROS 2 |

**Recommendation:** WebSocket with a small, versioned JSON (or CBOR for the ESP32 data plane) message envelope as the control plane; leave a clean seam to add MQTT (fleet fan-out) or Zenoh/gRPC (high-rate data plane) later without touching the semantic layer. Steal DDS's *QoS vocabulary* (reliable-vs-best-effort per stream, deadline, lifespan) as fields in your envelope, not as a transport.

### 3. Event logging and replay

The robotics-standard answer is **rosbag2 → MCAP**, now the default ROS 2 bag format (since Iron, 2023). MCAP is a chunked, indexed, append-only container with per-chunk compression (LZ4/Zstd), embedded/self-describing schemas, fast time-based seeking, and it's framework-agnostic (records ROS, Protobuf, JSON, FlatBuffers in one file). Even if you never touch ROS, **adopt MCAP as your log format** — it's tooling-rich (Foxglove Studio, `mcap` CLI, Rerun) and purpose-built for exactly the perception/decision/command streams you have.

Practical schema advice (synthesizing MCAP practice, event sourcing, and distributed-systems logging):
- **Record the "why," not just the "what."** The strongest published guidance: "Do not record only the high-bandwidth sensor topics. Record the low-rate supervisory topics that explain why the robot behaved the way it did" (command intent, state estimates, controller outputs, watchdog/safety events, rejected/degraded commands). For you: log every LLM prompt/response, every plan, every validator decision (accept/reject/clamp), every reflex trigger.
- **Timestamps:** stamp every event with (a) a **monotonic clock** for ordering within a device (immune to wall-clock jumps) and (b) a **wall-clock UTC** for cross-device correlation. Store both `t_captured` (at source) and `t_received` (at brain).
- **Clock sync across devices:** NTP (chrony) gets you a few ms on a LAN — sufficient for a hobbyist fleet; PTP (IEEE 1588) gets sub-µs if you ever need hardware-timestamped precision. Expect tens of ms of skew over Wi-Fi/Internet and **design for it**: a naive receive-timestamp can precede its send-timestamp and appear to violate causality. When precise ordering matters, add **Lamport/logical timestamps** or sequence numbers per stream.
- **Correlation IDs:** assign a `trace_id` per high-level task/goal and a `span_id` per command, threaded from LLM plan → command → body execution → feedback → log. This is the single highest-leverage thing for debugging an LLM-in-the-loop system and for deterministic replay.
- **Determinism:** to replay decisions deterministically, log every *nondeterministic input* to the decision layer (LLM outputs, RNG seeds, sensor frames, timestamps) so you can re-feed them. Treat the LLM as an external oracle whose outputs you record and can replay from the log (a "flight recorder" for the brain).

### 4. Safety and command validation layers

Even with **no motors yet**, build this scaffolding now — it's the cheapest when there's nothing to break, and retrofitting it is the classic compounding mistake.

- **Command validator (the "brain proposes, validator disposes" gate).** Every command — especially LLM-originated — passes through a deterministic validator *before* reaching a body: schema/type check, capability check (does this body advertise this action?), bounds/rate clamping, and policy checks. The LLM must never have direct actuator authority. This is the software analog of the industrial "Safe IO Cell" that acts as "an independent safety authority... supervising heartbeats and command envelopes."
- **Heartbeats/watchdogs, tiered.** Bodies and brain exchange heartbeats; loss triggers a safe state. Real systems use **tiered timeouts**: ArduPilot triggers RC/direct-control failsafe when the signal is lost "for greater than RC_FS_TIMEOUT (default = 1 sec)," and GCS/supervisory failsafe "If no heartbeat is received FS_GCS_TIMEOUT seconds (Default is 5 seconds)." The ROS-safety `software_watchdogs` package uses concrete leases (e.g., a 200 ms heartbeat with a 220 ms lease; optionally allow N misses before declaring failure). The failsafe should **latch** — stay in the safe mode until explicitly cleared, not silently resume (ArduPilot: "the copter will remain in its failsafe mode... will not automatically return to the flight mode that was active before").
- **E-stop semantics.** A dedicated, highest-priority stop path that bypasses normal command flow; on trigger, bodies go to a defined safe state (for a wheeled base: stop + brake; if already stopped, disarm — ArduPilot: "If the copter is armed but has landed, the copter will immediately disarm"). Industrial practice: dual-channel, monitored, fail-safe (absence of the "keep-going" signal = stop). Model it as "stop is the default; motion requires a continuously-refreshed permission."
- **Command TTL / lifespan.** Every actuation command carries an expiry; if the body doesn't get a fresh command within the TTL, it stops. This is ROS 2's **Lifespan QoS** ("the length of time a message is considered valid, after which time it will not be received") and it's how you make network loss inherently safe — stale commands can't keep a robot moving.
- **Graceful degradation on brain/network loss.** Define explicit degraded modes: (1) brain reachable → full autonomy; (2) brain slow/LLM down → fast-loop reflex only, conservative behavior; (3) brain unreachable → body-local safe hold. MQTT's **LWT + retained status topic** is the clean "who's alive / last known state" mechanism. The principle: **autonomy degrades toward safety, never toward uncontrolled motion.**
- **Minimal pre-motor safety set (build these first):** command schema validation + rejection logging; the versioned handshake with capability gating; heartbeat/watchdog with a safe-state transition; command TTL; a global E-stop message + state; and a DEGRADED brain state. All of this is exercisable with the laptop body and mock body — e.g., "kill the WebSocket, assert the mock body enters safe-hold within the TTL."

### 5. LLM-in-the-loop robotics

**The fast-loop/slow-loop split — what belongs where.** The consensus (SayCan → Code as Policies → Inner Monologue → Helix):
- **Slow loop (LLM/Claude, ~1–10 Hz or on-demand):** natural-language understanding, task decomposition, high-level planning, replanning on failure, tool selection, memory curation. Per Figure's official Helix announcement (Feb 20, 2025), S2 is "an onboard internet-pretrained VLM operating at 7-9 Hz" (7B params) for scene understanding and goal sequencing; the LLM answers "*what* needs to be done."
- **Fast loop (local, 10–200 Hz+):** reactive control, obstacle/collision reflexes, safety checks, sensor filtering, heartbeat. Helix's S1 is "a fast reactive visuomotor policy that translates the latent semantic representations produced by S2 into precise continuous robot actions at 200 Hz" (an 80M-parameter transformer); Helix 02 adds a whole-body control tier at 1 kHz. Fast loop answers "*how*, right now." On Apple Silicon this tier is local models via **Ollama/MLX** (VAD, wake-word, small vision, intent classification).
- **Grounding is the crux.** SayCan's core lesson: an LLM proposes plausible actions but is not grounded — pair each proposed skill with an **affordance/feasibility signal** (can this body actually do this now?) and pick `score = usefulness × feasibility`. Grounding roughly halved errors: PaLM-SayCan hit 84% planning / 74% execution in its training environment versus 67% planning for the ungrounded baseline. Your capability manifest *is* your affordance function: reject/deprioritize actions the current body can't perform. SayCan's other lesson: **the bottleneck is the skill repertoire, not the LLM** — invest in robust low-level skills/drivers.
- **Decouple the tiers as separate processes** (Helix's explicit design choice) so you can iterate on planning and control independently and so a slow/stalled LLM never blocks the reflex loop.

**Latency budgets.** Keep safety reflexes in the tens of ms locally; treat LLM planning as asynchronous and *never* on the critical control path. Helix keeps its whole control loop sub-100 ms by running everything onboard; you won't hit that with a cloud LLM, which is exactly why planning must be async and the fast loop autonomous between plans.

**Token/cost management.** Don't call the LLM every tick — call it on events (new goal, plan failure, significant state change, human utterance). Cache/reuse plans; use small local models for routine classification and reserve Claude for genuine planning. On edge/persistent agents, **KV-cache management dominates** — persisting/quantizing KV cache avoids expensive full re-prefill (one M4 Pro study: 15.7 s re-prefill per agent at 4K context without persistence).

**Context management for a persistent embodied agent.** Naively appending all observations causes "unbounded context growth and eventual degradation." Proven patterns:
- A **Memory Curator**: a separate LLM/process that *rewrites* (not appends) a bounded memory each step — compressing redundancy, resolving contradictions, discarding now-irrelevant detail.
- A **semantic-spatial memory graph** (entities: people, places, objects, task state) with **RAG retrieval** (semantic + positional + temporal queries) so the agent recalls "what/where/when" within human-like response times.
- Persist **task state** explicitly (a structured world/task model) rather than relying on chat history, so the agent survives restarts and can be replayed.

### 6. Voice interaction pipeline (Apple Silicon)

**Stack (all local, all proven on M-series):**
- **STT:** `whisper.cpp` with Metal (`-DGGML_METAL=ON`) or **MLX Whisper** — MLX is "a strong default local STT option" on Apple Silicon. Local STT cuts latency from ~300–800 ms (cloud) to ~50–300 ms; use `tiny.en`/`base.en` or quantized (`small-q5_0`) for near-real-time, and enable **VAD filtering** so Whisper doesn't transcribe silence.
- **LLM:** Ollama/MLX locally for the fast conversational tier; Claude for heavy planning.
- **TTS:** **Kokoro** (ONNX or MLX, incl. 4-bit) is the current quality/speed sweet spot on Apple Silicon; Piper was archived Oct 6, 2025 (still works as a Wyoming add-on but evaluate Kokoro/Coqui for new work). Voxtral/Qwen3-TTS are emerging higher-quality options as of 2026.
- **Glue:** the **Wyoming protocol** (from the Home Assistant ecosystem) is a clean, proven way to wire STT/intent/TTS as swappable services — worth mirroring conceptually as your voice adapter.

**Interaction mode & echo/interruption.**
- **Push-to-talk** is the simplest and most robust for a dev prototype (no false triggers). Add **wake-word** (openWakeWord, Porcupine) for hands-free. **Full-duplex** (continuous listen + barge-in) is the best UX but hardest.
- **Barge-in / interruption:** cut TTS the moment the user starts speaking (VAD-gated) — the "assistant's speech is automatically cut off if the user begins speaking again" pattern.
- **Echo cancellation:** with open speakers the mic hears the TTS; use AEC and/or gate the STT while TTS is playing (or duck/pause). Stream TTS sentence-by-sentence as the LLM generates so the user hears a response before the full generation completes.
- Treat the voice pipeline as **body #1's capabilities** (`microphone`, `speaker` capability types) flowing through the same adapter protocol and logging — don't special-case it.

### 7. Synthesis and recommendation

You are building, in effect, a **Viam-shaped control plane with a Helix-shaped brain**, using web-native transport and an LLM-orchestration core you already know how to build. Lean into that.

**Biggest compounding mistakes practitioners report (avoid these):**
1. **Assuming a reliable, in-order, low-latency network.** The #1 beginner failure. Design for loss, reordering, and delay from message #1 (TTL, idempotency, sequence numbers, heartbeats).
2. **Picking a heavyweight transport/framework (DDS/ROS 2) prematurely** and paying its complexity/discovery/scaling tax for value you don't use — then discovering (as the MoonBots team did, even on Wi-Fi 7) you have to swap the transport anyway.
3. **No versioning from day one**, so the first protocol change bricks existing bodies. Bake in the handshake + additive-only schema before body #2.
4. **Retrofitting safety and logging.** Both are near-free to add now with zero motors and brutally expensive later. Build the validator, watchdog, E-stop, TTL, correlation IDs, and MCAP logging into the skeleton.
5. **Putting the LLM on the control/safety path** (letting it directly actuate, or blocking the loop on its latency). Keep it advisory; ground it with affordances; validate its output.
6. **Unbounded LLM context** for a persistent agent — degrades and gets expensive. Use a curator + structured memory + RAG.
7. **Under-logging the "why."** Record decisions/intent/rejections, not just sensor streams, or you can't debug or replay.

**Recommended concrete design decisions (a shortlist to lock):**
- **Transport:** WebSocket control plane with a versioned message envelope (JSON for laptop/Pi/Jetson, CBOR option for ESP32). Clean seam to add MQTT (fleet fan-out) and Zenoh/gRPC (high-rate data plane) later. Do **not** start on DDS/ROS 2.
- **Adapter model:** Viam-style — standardized **capability-type APIs** (`camera`, `mic`, `speaker`, `drive`, `range`, …) + a generic `do_command` on every capability. Bodies are drivers that declare a **capability manifest** at handshake. Brain discovers via an explicit `list_capabilities`.
- **Versioning:** MCP-style handshake (client sends version → server echoes-or-alternatives → disconnect on mismatch); date/semver bumped only on breaking changes; effective capabilities = intersection. Additive-only schema with `reserved` retired fields; upgrade consumers before producers; versioned parallel channels for unavoidable breaks.
- **Orchestration:** three tiers — LLM slow loop (Claude, event-triggered planning, emits a behavior-tree-like plan) → local fast loop (reflex + BT execution + safety, on Ollama/MLX) → body drivers. FSM for the brain's own lifecycle; BT (LLM-generated, validator-checked) for tasks. Ground LLM proposals against the capability manifest (SayCan pattern).
- **Logging/replay:** MCAP from day one, with `trace_id`/`span_id` correlation, dual monotonic+UTC timestamps, and full capture of LLM I/O and validator decisions. NTP/chrony for clock sync; log logical sequence numbers per stream.
- **Safety layer:** command validator (capability + bounds + rate) gating all commands; tiered heartbeat/watchdog (≈1 s control link, ≈5 s supervisory) with latching safe-state; global E-stop path; command TTL/lifespan; explicit DEGRADED mode on LLM/network loss; MQTT-LWT-style liveness. All testable with the laptop + mock body before any motor.
- **Voice:** whisper.cpp/MLX (STT) + Ollama/MLX (fast LLM) + Kokoro (TTS), push-to-talk first then wake-word, VAD-gated barge-in and echo handling, exposed as body #1 capabilities through the same protocol.
- **Defer:** ROS 2 (add later only as one body adapter if you need its ecosystem), LeRobot/VLA (future learned body driver when manipulation appears), NVIDIA Isaac (only for heavy Jetson perception/sim), and MCP-as-control-bus (use MCP only for tools/introspection).

**Ecosystem direction as of mid-2026 (context for your bets):** the field is converging on (a) **Zenoh** displacing DDS as the scalable ROS transport (now an OSRF-shipped experimental RMW); (b) **MCAP** as the universal log format; (c) the **dual-system VLM+policy** architecture (Helix, π0, GR00T) as the standard embodied-AI shape; (d) **LeRobot** maturing into a full train/eval/deploy loop for VLAs (v0.6.0, July 2026); and (e) **MCP** spreading as the agent-tool standard (with explicit warnings against using it as a real-time robot control bus). Your web-native, LLM-orchestration-first, capability-driver design is well-aligned with where things are heading — the main risk is over-building infrastructure that mature open tools (Viam, MCAP, Wyoming) already give you, so borrow those rather than reinventing them.

## Recommendations

**Stage 0 — Skeleton (now, laptop + mock body, no motors).** Lock the WebSocket envelope + versioned handshake; implement the capability manifest + `list_capabilities` + `do_command`; wire MCAP logging with correlation IDs and dual timestamps; stand up the command validator, heartbeat/watchdog with latching safe-state, command TTL, E-stop message, and DEGRADED mode. *Benchmark to pass:* kill the socket and assert the mock body reaches safe-hold within the TTL, and that the whole exchange replays deterministically from the MCAP log.

**Stage 1 — Brain core.** Add the FSM lifecycle + fast-loop reflex tier (Ollama/MLX) + LLM slow loop (Claude) emitting validator-checked behavior-tree plans grounded against the capability manifest. Add the Memory Curator + structured task/world state + RAG. Add the voice pipeline as body #1 capabilities. *Benchmark:* the LLM can be slow/offline and the fast loop still keeps the system safe and responsive.

**Stage 2 — Second real body + fleet seams.** Bring up a real body (Pi/ESP32 sensor node) as a driver implementing the capability API; exercise the versioning path by making a backward-compatible schema change and confirming the old body still works. Add MQTT fan-out if you have >1 body. *Benchmark:* swap body hardware without changing brain code (the Viam test).

**Thresholds that change the plan:**
- If control-plane **latency over Wi-Fi becomes the bottleneck** → add Zenoh (or gRPC) as a high-rate data plane; keep WS for control/semantics.
- If you add **manipulation or learned skills** → integrate LeRobot/VLA as a body driver in the fast/skill tier; consider a Jetson body + Isaac ROS for perception.
- If you need **mature navigation/SLAM/manipulation stacks** → add a single ROS 2 *bridge body* rather than migrating the core.
- If bodies exceed **~10 or span multiple networks** → introduce MQTT/broker fan-out and per-body access control; revisit clock sync (PTP) only if you need sub-ms cross-device ordering.

## Caveats
- **Vendor/marketing sources:** Viam and Zenoh claims come partly from their own docs/benchmarks; treat performance numbers (Zenoh's latency/throughput advantages) as vendor-favorable and validate on your own network. Independent studies broadly corroborate "CycloneDDS best on wired Ethernet, Zenoh best on Wi-Fi/4G" — and note that in the single-machine wired benchmark DDS actually beat Zenoh (8 µs vs 10 µs), so Zenoh's edge is specifically wireless/WAN.
- **Figure Helix details** come from Figure's own announcements and secondary tech press, not peer review; the S2/S1 frequencies (7–9 Hz / 200 Hz; 1 kHz whole-body tier in Helix 02) and parameter counts (7B / 80M) are as *publicly described* by the company and should be read as architecture illustration, not independently verified specs.
- **ROS 2 on Apple Silicon** is improving fast but remains explicitly a "preview, not guaranteed production support" per the 2026 native demo; verify against the current release before relying on it.
- **Rapidly moving areas:** LeRobot (v0.6.0, July 2026), local TTS (Piper archived Oct 2025; Kokoro/Voxtral/Qwen3-TTS ascendant), and Ollama MLX support are all evolving month-to-month; re-check specific model/tool recommendations at build time.
- **Safety scope:** the safety patterns here are software scaffolding and functional-safety *concepts* (heartbeats, E-stop, validators). They are **not** a substitute for certified hardware safety (ISO 13849 / IEC 61508 safety relays, dual-channel e-stop) once real actuators with injury potential are involved — treat the software layer as necessary-but-not-sufficient.
- **Timestamp/clock claims** assume commodity NTP; sub-ms guarantees require PTP hardware you likely won't have on ESP32-class bodies — design ordering logic to tolerate tens-of-ms skew rather than assuming synchronized clocks.
- **SayCan success rates** (84%/74% training, 81%/60% real kitchen) are from a manipulation task suite on a specific mobile robot; they illustrate the *value of grounding*, not a number you should expect to reproduce in an inspection/sensing context.
